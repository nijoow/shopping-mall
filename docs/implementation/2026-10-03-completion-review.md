## 통합 검사

- `check:full`: 타입 생성·타입 검사·린트·26개 핵심 테스트·상품 7종/모델 5개/이미지 참조 12개·빌드·HTTP·브라우저 3흐름 통과.
- 격리 PostgreSQL 16: 독립 연결의 주문 중복/재고/환불/디자인 충돌, 29회 저장 뒤 동시 2요청 중 1개만 승인되는 429 경계 통과. 시간 창 경계로 흔들리지 않도록 이 테스트의 Date를 고정해.
- PostgreSQL 만료 계획은 원본을 변경하지 않고, 적용 시 만료 게스트만 삭제하며 최근 게스트를 유지하는 것을 확인했어.
- 실제 pg_dump/pg_restore로 별도 DB를 만들어 회원·주문·디자인 v3·공유 스냅샷을 복원했어. SQLite는 열린 WAL 백업/복원과 덮어쓰기 거절을 검증했어.
- 마지막 시각 검토에서 홈의 이전 러너 이미지 참조를 새 버전으로 맞추고, 캔버스 배경 위 보조 글자 대비를 높였어. 이는 표현 변경이며 이후 타입·린트와 해당 화면 확인을 별도로 수행해.
- 결과 로그와 화면은 Git 제외 `artifacts/2026-10-03-final/`, `artifacts/2026-10-03-3d-quality/`, `artifacts/browser/`에 있어.

## 직접 확인하고 바로잡은 문제

1. 브라우저 검증 보조 APIRequestContext가 HTTP loopback의 Secure 쿠키를 보내지 않아 별도 게스트를 만들었어. 앱 보안 설정을 바꾸지 않고 동일 페이지 fetch로 수정한 뒤 세 흐름이 통과했어.
2. PGDATABASE 환경 변수에 전체 URL을 넣던 백업 연결이 실제 실행에서 실패했어. 명시적 libpq 필드와 0600 임시 비밀번호 파일로 수정하고 실제 복원을 확인했어.
3. 하나의 429가 다른 작업까지 막던 클라이언트 대기 상태를 작업별로 구분했어. 입력 보존과 대기 후 재시도를 브라우저에서 확인했어.
4. 검색창 종료 직후 초점을 너무 일찍 측정한 결과는 실패 증거로 쓰지 않았어. 대화상자가 실제로 닫힌 뒤 원래 버튼으로 복귀하는 것을 확인했어.

## 소셜 실검증 상태

검증 주소는 `http://localhost:3000`, DB는 운영과 분리한 `.work/oauth-verification.sqlite`야. 실제 자격값은 기록하지 않았어.

| 제공자 | 확인                                                                          | 남은 조건                                                              |
| ------ | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Google | 실제 인증 페이지가 `401 deleted_client / The OAuth client was deleted`를 반환 | 유효한 클라이언트 ID/SECRET을 환경에 설정하고 성공·취소·실패·이관 검증 |
| Kakao  | 실제 계정 로그인 페이지까지 정상 연결                                         | 소유자 로그인/필요한 동의 후 callback·데이터 이관·로그아웃/재로그인    |
| Naver  | 실제 계정 로그인 페이지까지 정상 연결                                         | 소유자 로그인/필요한 동의 후 callback·데이터 이관·로그아웃/재로그인    |

공통 이관·소유권·중복 방지는 자동 테스트가 통과했지만, 실제 제공자 인증 성공의 증거로 대체하지 않았어. 새 키는 채팅·Git에 넣지 않고 로컬/배포 환경 설정에 저장해야 해. 제공자 콘솔의 callback도 검증 환경과 일치해야 해.

## 운영 반영 전

- 사용자 요청 범위에 맞춰 원격 CI/PR/배포를 별도로 진행해. 이번 변경에는 `operation_limits` 테이블/인덱스가 있어 배포 전에 올바른 운영 연결로 `db:setup`을 적용해야 해.
- 정리는 dry-run 계획과 대상·백업을 확인하고 명시적 적용 명령을 사용해. 이번 검증은 폐기 가능한 로컬 DB만 사용했어.
- 실제 iOS/Android·보조 기술·저사양 GPU 결과는 확인하지 않았어. 데스크톱 우선 요구에 맞춘 브라우저 폭 검사 및 소프트웨어 렌더러 결과와 구분해.
